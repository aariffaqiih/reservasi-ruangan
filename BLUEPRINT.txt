# BLUEPRINT SISTEM RESERVASI RUANG KAMPUS

## Versi Revisi

**Judul sistem:** Sistem Pengelolaan Reservasi Ruang Kelas Kampus di Luar Jam Perkuliahan

**Basis aplikasi:** Java, Spring Boot MVC, Thymeleaf, Spring Security, Spring Data JPA

**Target database revisi:** MySQL Server, dikelola melalui phpMyAdmin

**Tanggal audit blueprint:** 2 Juni 2026

## 1. Tujuan Dokumen

Dokumen ini adalah blueprint terbaru yang disusun berdasarkan:

1. hasil audit terhadap source code aplikasi saat ini,
2. perbandingan dengan blueprint versi sebelumnya,
3. pemetaan terhadap materi perkuliahan Java dan Object-Oriented Programming (OOP),
4. revisi pemilihan database dari H2 file database menjadi MySQL Server yang dikelola melalui phpMyAdmin.

Blueprint ini membedakan dua kondisi:

* **IMPLEMENTED**: sudah ada dan berjalan pada source code saat ini.
* **TARGET-MIGRATION**: keputusan desain baru yang harus diterapkan pada source code agar aplikasi memakai MySQL.

Catatan penting:

* MySQL adalah database management system (DBMS) yang menyimpan data aplikasi.
* phpMyAdmin adalah antarmuka web untuk membuat database, mengimpor SQL, melihat tabel, dan mengelola data MySQL.
* Aplikasi Java terhubung langsung ke MySQL melalui JDBC. Aplikasi Java tidak terhubung ke phpMyAdmin.

## 2. Latar Belakang Masalah

Mahasiswa sering membutuhkan ruang kelas kampus untuk kegiatan akademik di luar jam perkuliahan, misalnya diskusi kelompok, rapat kepanitiaan, persiapan presentasi, pelatihan, atau bimbingan.

Jika proses reservasi dilakukan secara manual atau informal, masalah yang dapat muncul adalah:

* jadwal penggunaan ruang bentrok,
* pemohon tidak tercatat dengan jelas,
* persetujuan admin tidak terdokumentasi,
* penggunaan ruang tidak terpantau,
* check-in dan check-out tidak tercatat,
* kendala atau pelanggaran sulit ditelusuri,
* riwayat reservasi tidak tersimpan dengan rapi.

Sistem ini dirancang untuk menangani proses tersebut dalam satu alur bisnis terintegrasi.

## 6. Use Case Utama

### UC-01 Login Pengguna

**Aktor:** Mahasiswa, Admin, Satpam

**Tujuan:** Memastikan pengguna masuk ke dashboard sesuai peran.

**Alur ringkas:**

1. Pengguna mengisi username dan password.
2. Spring Security membaca user dari database.
3. Password diverifikasi menggunakan BCrypt.
4. Sistem menyimpan identitas dan role ke session.
5. Sistem mengarahkan pengguna ke dashboard polymorphic berdasarkan `getDashboardPath()`.

### UC-02 Ajukan Reservasi Ruang

**Aktor:** Mahasiswa

**Include:**

* validasi data pemohon,
* validasi ruang aktif,
* validasi tanggal,
* validasi jam mulai dan jam selesai,
* validasi penggunaan di luar jam perkuliahan,
* cek bentrok jadwal.

**Hasil:** Reservasi baru tersimpan dengan status `PENDING` dan notifikasi dibuat.

### UC-03 Proses Approval Reservasi

**Aktor:** Admin

**Include:**

* verifikasi reservasi,
* cek status `PENDING`,
* cek ruang aktif,
* cek ketersediaan ruang,
* cek bahwa reservasi belum memiliki keputusan approval.

**Extend:**

* setujui reservasi,
* tolak reservasi,
* minta revisi data.

### UC-04 Kelola Penggunaan Ruang

**Aktor:** Satpam

**Include:**

* konfirmasi check-in,
* konfirmasi check-out.

**Extend:**

* catat kendala atau pelanggaran.

### UC-05 Batalkan Reservasi

**Aktor:** Mahasiswa

**Aturan:** Mahasiswa hanya dapat membatalkan reservasi miliknya sendiri pada status `DRAFT`, `PENDING`, atau `APPROVED`.

### UC-06 Lihat Status dan Riwayat

**Aktor:** Mahasiswa, Admin, Satpam

**Aturan akses:**

* mahasiswa hanya melihat reservasi miliknya,
* admin dan satpam dapat melihat data yang dibutuhkan sesuai fitur,
* notifikasi hanya dapat ditandai dibaca oleh penerimanya.

## 7. Alur Bisnis Utama

```text
Login
  -> Mahasiswa mengajukan reservasi
  -> Sistem memvalidasi data dan ketersediaan ruang
  -> Status PENDING
  -> Admin memverifikasi
      -> APPROVED
          -> Satpam check-in
          -> Status ACTIVE
          -> Satpam dapat mencatat kendala
          -> Satpam check-out
          -> Status COMPLETED
      -> REJECTED
      -> REVISION_REQUESTED pada approval
          -> Status reservasi disimpan sebagai REJECTED
          -> Mahasiswa membuat pengajuan baru setelah revisi
  -> Mahasiswa dapat membatalkan sebelum penggunaan aktif
  -> Status CANCELLED
```

## 8. Aturan Bisnis Aktual

### 8.1 Aturan pengajuan reservasi

* Pemohon wajib merupakan `Mahasiswa`.
* Nama dan NIM mahasiswa wajib terisi.
* Ruang wajib ada dan berstatus aktif.
* Tujuan reservasi wajib terisi.
* Tanggal reservasi tidak boleh kosong atau berada di masa lalu.
* Jam mulai wajib lebih awal daripada jam selesai.
* Pada hari kerja, reservasi hanya boleh dilakukan di luar jam kuliah `07:00-17:00`.
* Pada Sabtu dan Minggu, reservasi diperbolehkan tanpa batas jam kuliah tersebut.
* Jadwal tidak boleh bentrok dengan reservasi lain yang berstatus `PENDING`, `APPROVED`, atau `ACTIVE`.

### 8.2 Aturan approval

* Approval hanya boleh diproses dari status `PENDING`.
* Reservasi hanya dapat memiliki satu keputusan approval.
* Admin dapat memilih `APPROVED`, `REJECTED`, atau `REVISION_REQUESTED`.
* Keputusan `REVISION_REQUESTED` disimpan pada tabel approval, sedangkan status reservasi menjadi `REJECTED`.
* Versi aplikasi saat ini belum menyediakan edit dan resubmit pada reservasi lama.

### 8.3 Aturan akses ruang

* Check-in hanya boleh dilakukan pada reservasi `APPROVED`.
* Satu reservasi hanya dapat memiliki satu access record.
* Reservasi yang sudah check-in tidak boleh check-in ulang.
* Check-in mengubah status menjadi `ACTIVE`.
* Check-out mengubah status menjadi `COMPLETED`.
* Deskripsi kendala wajib terisi jika satpam membuat laporan.

### 8.4 Aturan pembatalan

* Mahasiswa hanya boleh membatalkan reservasi miliknya.
* Pembatalan diperbolehkan pada `DRAFT`, `PENDING`, atau `APPROVED`.
* Pembatalan ditolak pada `ACTIVE`, `COMPLETED`, `REJECTED`, atau `CANCELLED`.

### 8.5 Aturan notifikasi

Notifikasi dibuat pada perubahan penting, termasuk:

* reservasi diajukan,
* reservasi disetujui,
* reservasi ditolak,
* reservasi perlu direvisi,
* reservasi dibatalkan,
* check-in selesai,
* check-out selesai,
* kendala ruang dicatat.

## 12. Relasi Antar Kelas

### 12.1 Inheritance

```text
User <|-- Mahasiswa
User <|-- Admin
User <|-- Satpam
```

### 12.2 Interface implementation

```text
Notifiable <|.. Mahasiswa
Notifiable <|.. Admin
Notifiable <|.. Satpam
```

### 12.3 Association dan multiplicity

```text
Mahasiswa   1     -- 0..* Reservation
Room        1     -- 0..* Reservation
Reservation 1     -- 0..1 Approval
Reservation 1     -- 0..1 AccessRecord
Reservation 1     -- 0..* Notification
Admin       1     -- 0..* Approval
Satpam      1     -- 0..* AccessRecord
User        1     -- 0..* Notification
```

### 12.4 Catatan desain relasi

`Approval` dan `AccessRecord` diperlakukan sebagai association yang disimpan permanen untuk riwayat. Data tidak boleh ikut hilang hanya karena status reservasi berubah.

## 20. Revisi Database: MySQL Server dan phpMyAdmin

### 20.1 Keputusan target

**IMPLEMENTED pada starter:** database utama aplikasi menggunakan MariaDB/MySQL Server. phpMyAdmin digunakan sebagai alat administrasi database.

Nama database yang direkomendasikan:

```text
reservasi_ruang
```

### 20.2 Kondisi source code starter

**IMPLEMENTED pada starter:** migrasi teknis database utama sudah selesai.

Bukti kondisi saat ini:

* dependency runtime pada `pom.xml` memakai `com.mysql:mysql-connector-j`,
* `application.properties` memakai `jdbc:mysql://localhost:3306/reservasi_ruang`,
* schema dibuat/diperbarui otomatis oleh JPA/Hibernate seperti contoh dosen,
* `database/create_database.sql` tersedia untuk membuat database lokal,
* `database/verify_database.sql` tersedia untuk audit isi dan integritas relasi,
* H2 hanya dipakai pada test in-memory dengan `MODE=MySQL`.

### 20.3 Konfigurasi Spring Boot

Dependency runtime:

```xml
<dependency>
    <groupId>com.mysql</groupId>
    <artifactId>mysql-connector-j</artifactId>
    <scope>runtime</scope>
</dependency>
```

Konfigurasi datasource:

```properties
spring.datasource.url=jdbc:mysql://localhost:3306/reservasi_ruang?useSSL=false&serverTimezone=Asia/Jakarta&allowPublicKeyRetrieval=true
spring.datasource.driver-class-name=com.mysql.cj.jdbc.Driver
spring.datasource.username=root
spring.datasource.password=
```

Password production tidak boleh ditulis langsung ke repository.

### 20.4 Workflow database starter

1. Instal dan jalankan MariaDB/MySQL Server.
2. Buka phpMyAdmin jika ingin memeriksa data secara visual.
3. Jalankan `database/create_database.sql` jika database `reservasi_ruang` belum ada.
4. Jalankan aplikasi Spring Boot.
5. Biarkan Hibernate membuat atau menyesuaikan tabel melalui `ddl-auto=update`.
6. Jalankan `database/verify_database.sql` untuk audit isi database bila diperlukan.
7. Pertahankan H2 hanya sebagai database test in-memory.

### 20.5 Catatan kompatibilitas

Query repository dasar seperti `SELECT`, `INSERT`, `UPDATE`, `COUNT`, `JOIN`, dan
`FOR UPDATE` dapat digunakan pada MariaDB/MySQL. Repository final tetap harus memakai
parameterized query dan transaksi untuk alur kritis.

## 21. Transaksi dan Konsistensi Data

### 21.1 Transaksi serializable

Alur kritis memakai `@Transactional(isolation = Isolation.SERIALIZABLE)`:

* membuat reservasi,
* membatalkan reservasi,
* memproses approval,
* check-in,
* check-out.

### 21.2 Row locking

Repository memakai `SELECT ... FOR UPDATE` untuk:

* mengunci ruang ketika reservasi dibuat,
* mengunci reservasi ketika approval diproses,
* mengunci reservasi ketika check-in atau check-out diproses,
* mengurangi risiko race condition.

### 21.3 Constraint database

Constraint unik pada approval dan access record menjadi perlindungan tambahan jika dua request masuk hampir bersamaan.
